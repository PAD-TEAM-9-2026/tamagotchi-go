# Data warehouse and ETL

**Status: proposed.** The data warehouse and the ETL service that fills it (Lab 5).
The ETL service ([MihaelaCatan04/etl-service](https://github.com/MihaelaCatan04/etl-service),
submodule `services/etl`) reads the service databases through a read-only role,
transforms the rows into a star schema and loads them into a separate warehouse
database. Every service owner writes the extract files for their own data; the ETL
service owns the loader, the warehouse database and the run endpoints.

## Overview

```
service databases --(etl_reader, read-only port)--> ETL service --(upsert)--> warehouse
                                                       ^
                                     extracts/<source>-<table>.yaml, one per table
```

| Part | Where | Owner |
|---|---|---|
| Extract files | `extracts/*.yaml` in etl-service | the owner of the source service |
| `etl_reader` grants | each service's own migrations | the owner of the source service |
| `etl_reader` role | `deploy/db/init-service-databases.sh` | ETL service |
| Loader, schedule, run endpoints | etl-service | ETL service |
| Warehouse database | `deploy/compose.warehouse.yaml` | ETL service |
| Analysis queries | `queries/*.sql` in etl-service | contributed by PR, reviewed by the ETL service |

## Warehouse database

A separate PostgreSQL 17 container, `warehouse`, in `deploy/compose.warehouse.yaml`,
with its own volume. It is never one of the service databases and is not replicated:
it can be rebuilt from the sources by a full run (except rows already deleted at a
source, see [Deletes](#incremental-loads-and-the-watermark)).

| Setting | Value |
| --- | --- |
| Database / owner role | `WAREHOUSE_DB_NAME` / `WAREHOUSE_DB_USER` (default `warehouse` / `warehouse`), password `WAREHOUSE_DB_PASSWORD` |
| Host port | `127.0.0.1:5433`, for analysis only |
| Data tables | schema `public`: the tables in [Tables](#tables) |
| Loader bookkeeping | schema `etl`: `etl.runs`, `etl.extract_runs`, `etl.watermarks` |

The ETL service is the only writer. Analysis queries run read-only
(`BEGIN READ ONLY` or a read-only role).

## Star schema

Dimensions describe things (a user, a package, a creature); facts record events or
measurements and point at dimensions by their natural ID.

- Keys are the source's natural IDs (UUID v7), named `<entity>_id`: a fact's
  `battle_id`, `winner_id` and `package_id` join to `dim_user.user_id`,
  `dim_package.package_id` and so on. No surrogate keys.
- **No foreign keys** in the warehouse. Sources load independently and at different
  times, so a fact may arrive before its dimension row. Joins are by ID.
- `dim_date` is generated by the loader (one row per day, 2026-01-01 to 2027-12-31:
  `date`, `year`, `month`, `day`, `iso_week`, `weekday`). Facts keep exact timestamps
  and join with `(<column> AT TIME ZONE 'UTC')::date`.

## Tables

Each table is loaded by exactly one extract file, owned by the source service's owner.
An owner may add tables for their own domain through a PR to etl-service; the table
then appears here in the same PR to Shared.

| Table | Source | Grain (one row per) |
| --- | --- | --- |
| `dim_user` | user-management | user |
| `dim_package` | package-registry | package |
| `dim_boss` | package-registry | boss |
| `dim_creature` | tamagotchi | creature |
| `dim_guild` | guild | guild |
| `dim_date` | generated by the loader | day |
| `fact_battle` | battle | battle |
| `fact_currency_movement` | user-management | wallet credit, battle settlement or reversal |
| `fact_xp_award` | tamagotchi | XP award |
| `fact_notification_delivery` | notification | notification delivery |
| `fact_raid_participation` | monster-raid | player in a raid |
| `fact_map_activity_hourly` | map | hour and area |
| `fact_guild_membership_daily` | guild | guild and day |

The columns of each table are defined by its extract file (`columns`, below), which is
reviewed in etl-service. The loader creates the table from it, with `key` as the
primary key. When a merged change alters `columns` or `key`, the next run drops and
recreates that table and reloads it in full (its watermark is reset). Other tables are
not touched.

## Extract files

One file per target table, in etl-service, named `extracts/<source>-<table>.yaml`,
for example `extracts/tamagotchi-dim_creature.yaml`.

```yaml
# extracts/package-registry-dim_package.yaml
source: package-registry
table: dim_package
description: One row per package, its current name, status and config version.
key: [package_id]
watermark: updated_at
columns:
  package_id: uuid
  name: text
  status: text
  config_version: integer
  created_at: timestamptz
  updated_at: timestamptz
query: |
  SELECT package_id, name, status, config_version, created_at, updated_at
  FROM packages
  WHERE updated_at > :watermark
```

| Field | Required | Rule |
| --- | --- | --- |
| `source` | yes | One of `user-management`, `battle`, `tamagotchi`, `notification`, `guild`, `package-registry`, `map`, `monster-raid`. |
| `table` | yes | The target table, `dim_<name>` or `fact_<name>`, snake_case, matching the file name. |
| `description` | yes | One sentence: what one row is. |
| `key` | yes | Non-empty list of columns that identify a row. The loader upserts on it, so it must be unique in the query result. |
| `watermark` | yes | The name of a `timestamptz` column of the result for incremental loads, or `null` for a full reload. |
| `columns` | yes | Ordered map `name: type`, exactly the columns the query returns, in the same order. |
| `query` | yes | One `SELECT` (or `WITH … SELECT`) against the source database, no trailing `;`. |

**Column names** are snake_case. Times are `timestamptz` in UTC and end in `_at`;
IDs are `uuid` and end in `_id`. **Allowed types:** `uuid`, `text`, `boolean`,
`smallint`, `integer`, `bigint`, `numeric`, `date`, `timestamptz`. No arrays, JSON or
binary. Store enum values as lowercase text labels (for example
`CASE "Status" WHEN 2 THEN 'completed' … END`), so the warehouse can be read without
the source code.

The loader rejects a file that breaks any rule above. A rejected file fails only its
own extract; the other extracts of the run still load. CI in etl-service validates
every file, so a broken one cannot be merged.

## Incremental loads and the watermark

When `watermark` names a column, the query must filter with exactly one placeholder,
`:watermark`:

```sql
WHERE awarded_at > :watermark
```

- `:watermark` is bound as a `timestamptz` **parameter**, never pasted into the SQL text.
  It is the only named placeholder; `::` casts such as `created_at::date` are fine.
- The first run binds `1970-01-01T00:00:00Z`.
- After a successful load the loader stores the maximum value of the watermark column
  among the rows it read. A run that reads no rows keeps the old watermark.
- Every run binds **the stored watermark minus 5 minutes**. Rows committed late with a
  timestamp up to 5 minutes earlier, or not yet on the replica, are read on the next run. The upsert on
  `key` makes the overlap harmless, which is why `key` must be unique per row.
- Rows whose watermark column is `NULL` never match. Filter or fill them in the query.

When `watermark` is `null`, the query has no placeholder and every run reloads the
whole table: delete and insert in one warehouse transaction, so readers see the old
or the new table, never a mix. Use it for dimensions and small tables, or for sources
without a change timestamp (Battle's `Battles` has none today).

**Deletes:** an incremental extract never sees a row deleted at the source; it stays in
the warehouse. Use a full reload, or a status column, where that matters.

## Source access: `etl_reader`

- `etl_reader` is a `LOGIN` role, created by `deploy/db/init-service-databases.sh`
  **before** any service schema is loaded, with `default_transaction_read_only = on`
  and `CONNECT` on every service database. Password `ETL_READER_PASSWORD`.
- Each owner grants `SELECT` on exactly the columns their extracts read, in their own
  migrations, column by column where a table holds anything private:

  ```sql
  DO $$ BEGIN
      IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'etl_reader') THEN
          GRANT SELECT (package_id, name, status, config_version, created_at, updated_at)
              ON packages TO etl_reader;
      END IF;
  END $$;
  ```

  The guard keeps migrations working where the role does not exist. Because the
  migration is recorded as applied either way, the role must already exist when it runs:
  that is why the init script creates it first.
- The loader connects as `etl_reader` to every source database:
  `ETL_SOURCE_HOST` / `ETL_SOURCE_PORT`, the database names from the existing
  `*_DB_NAME` settings. With the HA overlay this is the **read-only port 5001** of
  `pg-haproxy` (database HA contract, proposed in #342), so the ETL never loads the
  primary.
  Replica lag is covered by the 5-minute overlap.
- Each extract runs in a `READ ONLY` transaction with a 30-second `statement_timeout`,
  and the loader reads in batches of 5,000 rows.

**No personal data or secrets** in the warehouse: no usernames, display names, emails,
passwords or hashes, tokens, push tokens, device IDs, IP addresses, free text written by
players (chat, messages, descriptions) or exact coordinates. Map data is aggregated per
hour and rounded to about 1 km. User IDs are allowed: they are the join key and identify
no one outside the system.

## Runs

- A run loads every valid extract. Each extract loads in its own warehouse transaction
  together with its new watermark, so a failed extract changes nothing and is retried in
  full on the next run.
- Only one run at a time (a PostgreSQL advisory lock in the warehouse).
- A run starts at startup once the warehouse is reachable, then every
  `ETL_INTERVAL_SECONDS` (default 300), and on `POST /v1/etl/runs`.
- Run status: `RUNNING`, then `SUCCEEDED` (every extract loaded), `PARTIAL` (some failed)
  or `FAILED` (none loaded). Extract status: `SUCCEEDED`, `FAILED` or `REJECTED` (invalid file).
- A run that finds a source database unreachable fails that source's extracts and
  continues with the rest.

## Endpoints

Served on the ETL service's own port (3011), not through the Gateway, like the
Broker's management endpoints.

| Method and path | Request | Response | Access |
| --- | --- | --- | --- |
| `POST /v1/etl/runs` | none | 202 EtlRun (`RUNNING`) | admin |
| `GET /v1/etl/runs` | query `limit` (1-100, default 20), `before` | 200 EtlRunPage, newest first | admin |
| `GET /v1/etl/runs/{runId}` | none | 200 EtlRun with its extracts | admin |
| `GET /status` | none | 200 Status, or 503 when `DOWN` | direct, Service Discovery |
| `GET /health`, `GET /ready` | none | 200 or 503 | direct |
| `GET /metrics` on `METRICS_PORT` | none | Prometheus text | monitoring network only |

**Admin** is the same as the Broker's management endpoints: one User Management access
token (`Authorization: Bearer`, RS256, `typ` at+jwt, `iss` tamagotchi-go-users, `aud`
tamagotchi-go, at most 900 s) with the `admin` role, verified against User Management's
JWKS. Missing or invalid token 401 `unauthenticated`, a user who is not an admin 403
`admin_required`, keys unavailable 503 `auth_keys_unavailable`.

Errors are Problem Details (RFC 9457): 400 `validation_error` (bad `limit` or cursor),
404 `run_not_found`, 409 `etl_run_in_progress` (a run is already running; the body
carries its `run_id`), 503 `dependency_error` (warehouse unreachable).

`/status` follows the shared [Status](../docs/field-types.md#status) shape: `DOWN` when
the warehouse is unreachable, `DEGRADED` when the last run was `PARTIAL` or `FAILED`.
The service registers with Service Discovery on startup like every other service. It
is not a Broker destination: no gRPC endpoint and no subscriptions.

## Observability

- JSON log lines with a fixed message and fields: `etl run started`, `etl run finished`
  (`run_id`, `status`, `duration_ms`), `extract loaded` / `extract failed`
  (`file`, `rows_read`, `rows_upserted`, `error`). Never row values.
- Metrics: `etl_runs_total{trigger,status}`, `etl_extract_rows_total{table}`,
  `etl_extract_failures_total{table}`, `etl_run_duration_seconds`,
  `etl_last_success_timestamp_seconds{table}`.

## Acceptance

- Every extract file passes validation in etl-service CI.
- A first run fills every table; a second run with no source changes reads only the
  5-minute overlap and leaves the warehouse data unchanged.
- A source row updated after a run appears in the warehouse after the next run.
- A failing source fails only its own extracts and the run is `PARTIAL`.
- A full-reload table is never seen half-loaded.
- `etl_reader` cannot write to a source database or read a column that was not granted.
- `POST /v1/etl/runs` while a run is running answers 409 `etl_run_in_progress`.
