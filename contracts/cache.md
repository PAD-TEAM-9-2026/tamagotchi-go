# Cache and consistent hashing

**Status: proposed.** The sharded read cache every service uses for common GETs and
user lookups. Each service talks to the shards directly through its language kit
(`kits/typescript`, `kits/csharp`); there is no cache proxy. Every kit must pass
[cache-ring-vectors.json](cache-ring-vectors.json).

## Nodes

```
CACHE_NODES=cache-0=cache-0:6379,cache-1=cache-1:6379,cache-2=cache-2:6379
```

- Comma-separated `name=host:port`. Spaces around entries are ignored, the order is not significant.
- A name is unique and non-empty. A duplicate name or an entry without `=` stops startup.
- The ring uses the **names** only. Changing an address does not move any key.
- Unset or empty `CACHE_NODES` turns caching off: every read goes to the database and the response carries `X-Cache: MISS`.

## Ring

| Rule | Value |
| --- | --- |
| Hash | first 8 bytes of `MD5(text)` read as a big-endian unsigned 64-bit integer; `text` is UTF-8 |
| Virtual nodes | 128 per node, the point of node `name` number `i` (`0..127`) is `hash("{name}#{i}")` |
| Order | points sorted ascending; equal points go to the lower node name (ordinal string comparison) |
| Placement | `hash(key)`, then the first point `>=` it, wrapping to the first point after the last |

MD5 only spreads keys; it is not used for security. Node, .NET and Python all have it
built in. TypeScript must use `BigInt`, C# `ulong`.

Adding or removing a node moves only the keys the changed node gains or loses, about
`1/N` of them. With `hash(key) % N`, going from 3 to 4 nodes would move about 75%.

## Test vectors

[cache-ring-vectors.json](cache-ring-vectors.json) is generated by the reference
implementation [tools/cache_ring.py](../tools/cache_ring.py) and checked in CI.

```json
{
  "virtual_nodes": 128,
  "keys": [{"key": "tamagotchi:v1:creature:...", "hash": "<unsigned 64-bit, decimal string>"}],
  "cases": [
    {"name": "three_nodes", "nodes": ["cache-0", "cache-1", "cache-2"],
     "first_points": [{"point": "...", "node": "..."}], "last_point": {"point": "...", "node": "..."},
     "expected": {"<key>": "<node>"}}
  ]
}
```

- 200 keys: realistic keys of every service, query-hash keys, keys equal to a point
  (`cache-0#0`), a non-ASCII key, a one-character key, a 320-character key and keys past
  the last point that wrap around.
- Cases: `three_nodes`, `cache_1_removed`, `cache_3_added`.
- A kit passes when every `hash` and every `expected` node match. Hashes and points are
  decimal strings because JSON numbers lose precision above 2^53.
- `python tools/cache_ring.py` regenerates the file, `python tools/cache_ring.py --check` verifies it.

## Failure behaviour

| Event | Behaviour |
| --- | --- |
| Node temporarily down: a command errors or takes longer than **50 ms** | Mark the node down for **10 s**, count `result="error"` and read from the database. Its keys are **not** moved to another node. While it is down, its keys are neither read nor written. After 10 s the next command tries it again. |
| Node removed from or added to `CACHE_NODES` (config change, restart) | The ring changes and about `1/N` of the keys move. Keys that now live elsewhere simply miss once. |

The cache is optional: a cache failure never turns into an error response.

## Keys

```
{service}:v1:{resource}:{id}[:{query}]
```

- `service` is the logical service name, `resource` a short noun of that service.
- Anything specific to one user includes the user id.
- `query` is the first 16 hex characters of `SHA-256` of the normalized query: the
  parameters that change the response, sorted by name then value, percent-encoded and
  joined with `&`. Omitted when the response does not depend on a query.
- Never cached: tokens, password hashes, refresh tokens or any other secret.

## Values and TTL

The value is JSON: `{"body": <response body>, "etag": "<etag>" | null, "cached_at": "<ISO-8601 UTC>"}`.

| Data | TTL |
| --- | --- |
| Money (wallets, balances) | at most 5 s |
| Other domain data | at most 1 h, the owner picks a shorter one where it fits |
| Immutable versioned config (by `config_version`) | may have no TTL |

Writes use `SET key value EX ttl` after a database read that missed.

## Invalidation

- The write path deletes the affected keys **after** its database commit.
- Event consumers delete the keys for the facts they receive.
- A failed delete is counted as an error and not retried; the TTL bounds the staleness.
- No in-process cache of domain data, because replicas would go stale. The only
  exception is the JWKS document.

## Observability

- Metric `cache_requests_total{service,node,result}` with `result` = `hit`, `miss` or
  `error`, and `node` the node name.
- Header `X-Cache: HIT` or `X-Cache: MISS` on every response of a cached operation.
- The Gateway forwards only the headers listed in each operation's `response_headers` in
  [operations.v1.json](operations.v1.json). Each owner adds `x-cache` to the operations
  they cache, in their own PR.

## Deployment

`deploy/compose.cache.yaml` runs `cache-0`, `cache-1`, `cache-2` on Valkey 8 with no
persistence, a `maxmemory` limit and `allkeys-lru`. Until it lands, a single local
Valkey with `CACHE_NODES=cache-0=localhost:6379` works: the ring is valid with one node.
